# День 8

Проблемы без брокера сообщений

Если мы сделали запись в один сервис а следующий отказал то нужно либо проглатывать ошибку либо  отменять отменять транзакцию в другом сервисе 
Если сервис долго отвечает то происходит каскадное падения от нехватки потоков

Брокер решает тем что отправитель не ждет получателя а кладет сообщения в брокера и уходит, освобождая поток 

RabbitMQ base

**Queue** (очередь — хранит сообщения; только она их хранит).
**Exchange** - роутер в RabbitMq. Он не  хранит сообщения а по routing key  и bindings решает в какую очередь положить
**Binding** -  (привязка — правило «эта очередь подписана на этот exchange»).

Публикация 
мы  пишем в обменник а сообщение переправляется внутри на очередь

**Routing and Consume** - получаем сообщение от отправителя и дублируем его в очереди, consumer-ы принимают его. 

**Publisher/Subscriber** - дублирование сообщений в очереди
(Point-to-Point) - распределение сообщений между подписчиками внутри одной очереди 

Routing key - строка которая дает понять exchange в какие очереди отправлять
##### 4 типа exchange

**Headers** - routing key игнорируется, используются только заголовки для определения
**Fanout** - ключ не важен, сообщение идет во все очереди exchange которые привязаны
**Direct**  - routing key должен точно совпадать с binging key очереди.
**Topic** - routing key делится точками на слова и происходит совпадение по шаблонну `*` = одно слово, `#`= 0 и больше слов 


**Ack** - подтверждение сервиса что он обработал и можно удалять сообщение из очереди.

Брокер не удаляет сообщение из очереди пока consumer не обработает его и не даст сигнал "обработал, можешь удалять"

**reque** - при обработке возникла ошибка и запрос делается заново
**negative acknowledgement**- это когда consumer взял в обработку но по мере обработки выбрасывается исключение (неправильно введенные параметры) и тут смотрим на флаг
`reque=false` запрос отправляем в DLX, если DLX не настроен то  сообщение удаляется, `reque=true` запрос возвращаем в очередь

prefech - ограничитель  на отправку сообщений за раз, ждем ack от получателя и шлем следующее сообщение

для чего: если нам важно быстрее раскидать кучу то ставим большой prefetch, если у нас мало памяти (все взятые запросы хранятся и ждут пока их обработают ) то ставим маленький prefetch (  обработается ,просто не так быстро ). Если не поставить prefetch то один сервис заберет себе все сообщения и будет обрабатывать, а другие будут проставить.
