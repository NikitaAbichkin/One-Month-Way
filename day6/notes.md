Он не может ее заинлайнить потому что для него method.invoke() черный ящик значение которого зависит от внешних данных которые приходят в Runtime.

В HTTP/1.1 На одном TCP соединении может быть максимум один живой запрос, пока он выполняется другие не могут передавать данные по этому соединению.


#### Как работает gRPC

Мы передаем только (тип данных, значение ) - (int64, 1200)

Есть договоренность что 1 по счету это `age`, второй по счету это `name`  они могут идти в разном порядке, важно то какие он по (номеру внутри ) идут 

Номер берется из контракта файла ( `.proto` )

1 байт = 8 бит 
3 правых бита — wire type (способ кодирования: varint, 64 бита, длина+байты, 32 бита)
следующие 4 бита — номер поля
самый левый бит — флаг «есть ли следующий байт» (тег сам является varint)
Поэтому номера полей 1–15 влезают в 1 байт.

##### как определяется какое число если оно выходит за рамки 1байта 

в самом начале 1 или 0 означает кончилась запись или нет

1 (010 1010) 7 битов определяют число а самая первая цифра опрееделяет число кончилось или нет если нет то мы берем следующий байт 

0 0000010 - 0 в конце означает что нужно взять все до единицы ( справа налево и совместить с числом из прошлого байта )

10 + 010 1010  = 10 010 1010

Быстро потому что быстрее передать несколько бит и не нужно тратить время на парсинг

#### Была проблема http1.1

Соединение между клиентом и сервером это непрерывный поток байтов. Соеднение дает сделать только один синхронный запрос, второй обязан ждать окончания первого потому что ему нужно различать какие байты послал первый а какие послал второй 

Решение http/2

**frame** - кусок данных 

Каждый фрейм имеет заголовок , внутри фрейма лежит вся нужная мета информация (сколько байт внутри, к какому запросу данный фрейм принадлжит)

кусок данных который шлют по через стрим внутри ТСП соединения(идут асинхронно).В заголовке имеет свой StreamId. Когда ответ  приходит обратно то то  JVM смотрит на StreamId фрейма и понимает к какому запросу это было адресовано.

**Стрим** - Один запрос внутри соединения, у него свой Id, фреймы помечены этим Id чтобы, чтобы JVM понимала какой фрейм к какому запросу относится.

**Мультиплексирование**  - когда фреймы идут не синхроно а  по мере выполнения 

ОС собирает байты из TCP-пакетов в единый поток, а фреймы парсит библиотека в JVM : она считывает заголовки фреймов, смотрит на `Stream ID` и направляет данные в нужный буфер запроса.

В обычном сетевом запросе заголовки не сохраняются и их нужно парсить каждый раз 


#### 4 типа RPC

RPC - вызов метода на другом сервере 

**Unary RPC**  ( один к одному ) - один запрос  на сервер, сервер вызвает функцию и дает один ответ.

**Server Streaming RPC** - один запрос на сервер, сервер а сервер отправляет сообщения пачками 

**Client Streaming RPC** - Клиент шлет поток запросов, сервер отвечает одним ответом.

**Biderectional Streaming RPC** - двунаправленный поток данных со стороны клиента и со стороны сервера ( оба шлют по мере обработки  не дожидаясь финального сигнала )


Внутри одного TCP соединения может проходить  множество stream-ов 

**Deadline** - промежуток времени по истечению которого вызов считается несостовяшимся 
*Примечание*:  если требуется доп вызов другого сервиса то он отнимает от общего времени сколько ему пришлось потратить и передает уже остаток тому серверу 


### Итог:

gRPC быстрее потому что 
1) Четко скомпилированные файлы через которые происходит мапинг и есть контракт быстрее чем reflection потому что JIT может заинлайнить
2) Весят меньше из за того что не приходится тратить байты на (название, ковычки, запятые, двоиточие )
Как gRPC читает байты 
- тег: правые 3 бита — wire type, следующие 4 — номер поля, левый бит — флаг продолжения
- если левый бит байта = 1, нужно взять следующий байт, чтобы получить число
Как gRPC отправляет данные
- Внутри одного TCP соединения стримы пишут фреймы которые передаются по ТСП ( так же можно из с json)

#### Рефлексия и то как она работает 

**Constant pool** - пул констант с описаниями ( до первого вызова, после под номерами лежат прямые ссылки)
**Мегаморфность** - на одном и том же участке кода побывало 3+ классов у `reciever-а` 
**Inline cache** - проверка на класс + прямой вызов закэшированного адреса метода (без поиска по vtable).

**Реализация Метода**  - живете в метаспейс своего класса

#### Почему рефлексия медленная

**Мегаморфный вызов внутри**
Метаморфный вызов нельзя заинлайнить  в связи с тем что внутри мы вызываем интерфейс `MethodAccessor` который мы не можем заинлайнить ибо внутри могут лежать разные классы с реализацией. Мы не можем 100 процентов заинланить 

**Проверка доступа вызова функции в данном участке кода**
Каждый раз когда мы вызываем функцию происходит проверка а можно ли ее тут вызвать (Javac не знает какой метод вызовется, так что проверку оставил на рантайм)

**Boxing and OutBoxing**
так как метод invoke принимает аргументы через `Objcect[]` то  нужно упаковать аргументы и внутри распоковать.
