2xx - усешный запрос 
4xx - ошибка на стороне клиента
5xx - ошибка на сервере 


### Коды для заказа

| Код                           | Название                         | Когда для `/orders`                 |
| ----------------------------- | -------------------------------- | ----------------------------------- |
| **200** OK                    | успех, есть тело                 | `GET /orders/42` нашёл заказ        |
| **201** Created               | создан новый ресурс              | `POST /orders` создал заказ         |
| **204** No Content            | успех, тела нет                  | `DELETE /orders/42` удалил          |
| **400** Bad Request           | клиент прислал невалидные данные | `quantity: -5`                      |
| **404** Not Found             | ресурса не существует            | `GET /orders/999`                   |
| **409** Conflict              | конфликт состояния               | заказ уже отменён, повторная отмена |
| **500** Internal Server Error | необработанное исключение в коде | NPE в контроллере                   |

Версионирование API

**URI versioning**

```
GET /api/v1/orders/42   → один контроллер
GET /api/v2/orders/42   → другой контроллер
```
**Совпадение по пути + заголовку ( нужно чтобы пришел запрос с заголовком  Accept)**
```java
GET /orders/42 Accept: application/vnd.myapp.v2+json

@GetMapping(value = "/orders/42", produces = "application/vnd.myapp.v1+json") OrderV1Dto getOrderV1(...) { ... }
```

**Совпадение по параметру **
```java
GET /orders/42?version=2

@GetMapping(value = "/orders/{id}", params = "version=2")
OrderV1Dto getOrderV1(...) { ... }
```



Breaking change (ломающее изменение )
Любое измение ведущее к тому что у принимающего сервера нету параметра который ему нужен чтобы создать обьект.

Если удалить строку во время выполнения offset между двумя запросами то мы пропустим значения которые должны были быть  из за того что значения сместились и мы должны пропустить их 


### Практика: REST API для `order`

**Модель `Order`:** `id`, `productId`, `quantity`, `status` (`NEW`, `PAID`, `SHIPPED`, `CANCELLED`). 
**Хранилище:** обычная `Map` в памяти. БД сегодня не нужна, фокус на REST. Параллельные запросы пока не учитываем.

#### Эндпоинты (префикс `/api/v1`)

| Метод и путь                                     | Успех                                           | Ошибки                                                |
| ------------------------------------------------ | ----------------------------------------------- | ----------------------------------------------------- |
| `POST /orders`                                   | `201` + заголовок `Location` + тело заказа      | `400`, если `quantity <= 0` или нет `productId`       |
| `GET /orders/{id}`                               | `200`                                           | `404`                                                 |
| `GET /orders?page=0&size=20`                     | `200`, список заказов, отсортированный по `iыd` | `400`, если `size > 100` или `page < 0`               |
| `PATCH /orders/{id}` с телом `{"status": "..."}` | `200`                                           | `404`; `409`, если заказ уже `CANCELLED`              |
| `DELETE /orders/{id}`                            | `204`                                           | нет (повторный вызов тоже `204`, это идемпотентность) |

#### `Idempotency-Key` для `POST`

- Заголовок обязателен. Если его нет, верни `400`.
- Ключ новый: создаёшь заказ, сохраняешь ключ и ответ (статус + тело).
- Ключ уже есть: заказ **не** создаёшь, возвращаешь сохранённый ответ.

#### Требования
- Входные и выходные данные через **DTO** (отдельные классы для запроса и ответа), не через `Order` напрямую.
