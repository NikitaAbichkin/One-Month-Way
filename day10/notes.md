В RabbitMQ 

Имя очереди в кластере = уникальный ключ.

Очередь это один файл + один запущенный процесс в RAM. Нельзя добавить узел который будет иметь доступ к очереди другого , для обмена нужны переговоры по сети ( это долго ).

Решается тем что мы на каждом узле пишем свою  очередь с другим названием  ( которая выполняет те же действия).

### kaffka 

**Партиция** - файл на диске в который можно только записывать в конец 
**Топик** - имя за которым стоит набор партиций. Расположен в метаданных кластера.

Поток  сообщений разбит на партиции
**Адресация** - Через имя топика  получаем список партиций и их нахождение.
Выбор партиции - в продюсере на каждое сообщение.По умолчанию `hash(key) % N`, можно заменить своей логикой.(Партишинер сам  выбирает куда писать )


kaffka хранит сообщения внутри файла, даже после того как отдали его.
**Retention** - удаление данных, по какой то  величине  (время, размер ) а не по факту чтения.
**Page cache** - область памяти в RAM куда ОС складывает страницы файла перед записью.

**Offset** - номер записи внутри  партиции
**Segment** - кусок партиции определенно-фиксированного размера
`.log` - сами данные ( где название файла,  это офсет с которого идет счетчик)
`.index` - файл который имеет разреженную карту файла, каждый 4кб в `.log`, тут  записано расположение порядкового элемента с номером байт. Нужно для быстрого поиска.

(round-robin) - принципе по которому сообщения отправляются по партицям по кругу.
(Ключ) - значение по  которому вычисляем хеш и определяем в  какую  партицию положить  значение. (всегда одинаково будем ложить в определённую партицию )

##### Почему  увеличивать партиции больно 
Если мы все время ложили данные с ключем "100" в партицию#1, то щас мы будем ложить ее в другую. Каждую партицию читает разный consumer, может нарушиться порядок обработки.

Порядок сообщений определяет брокер, а не отправитель - внутри офсет файлы лежат не в логической последовательности. От кого первого ему пришло сообщение от того  из записал.

Как гарантировать  порядок
1) Делать запись в одну партицию по ключу
2) Настройка записи "батчей", продюсер нумерует батчи и  те батчи  что пришли в неправленом порядке отклоняются
3) Один процесс продюсер

Почему продюсер может  делать  ретрай  - во всех случаях когда скинули сообщения брокеру но не получили ответ.
#### Consumer Group 

Консюмеры определяются в группы чтобы сообщения между ними  разъединялись.

 Одну партицию в группе читает максимум один consumer. Один consumer может читать несколько партиций.( потому что консюмеры не могут договорится между собой кто будет сообщение читать и обрабатывать)

Каждая группа читает все партиции. А уже кому какая партиция достанется на обработку определяется внутри группы.

Раз в определенный промежуток времени consumer делает коммит на партиции (на каком offset он остановился, в случае падения или замены он обращается  к брокеру и получается последнюю позицию и не читает с начала)

Порядок «обработал → закоммитил» определяет гарантию
Ручной коммит дает нам право определить момент коммита, давая право на `at least once`(сделать коммит по факту записи а не принятия сообщения)

#### Rebalance 

**Rebalance** - процедура заново поделить партиции между текущими членами группы.

**Лидер(Consumer)**  - главный Consumer которому брокер отправляет список участников группы и чтобы Consumer решил кому сколько достанется. Потом план уходит координатору и он рассылает его всем. 
**heartbeat**- сигнал который отправляют координатору(брокеру) раз в 3 секунды ("я живой")

**Координатор** - один из брокеров выполняет роль координатора и при rebalance он дает указание лидеру среди группы.


3 консюмера 3 партиции, один консюмер  упал (партиция остались без читателя)От упавшего перестают поступать  heartbeat и через 45с считается мертвым, координатор отправляет всей группе сообщение что  нужно делать ребаланс, каждый `consumer` ставит пометку `offset`(сколько он прочитал) и отпускает партицию, После координатор  выбирает лидера который определит какая партиция какому consumer-у достанется

Каждый консюмер отпускает файл и ставит пометку до куда он дочитал.
 

session.timeout.ms - сколько ждет координатор чтобы посчитать  консюмера мертвым
max.poll.interval.ms -  сколько ждёт следующего запроса за сообщениями

### Итог
Партиция  - файл, один читатель в группе, чтобы не было переговоров кому сообщение должно достаться( Один брокер может держать несколько партиций внутри себя.)
Ключ определяет партицию, партиция определяет порядок
Сообщение не удаляется поэтому читать может каждый
Ретрай ломает порядок(возникает из за того что не получили сообщение от  брокера, причина не важна), Порядок чинит нумерация батчей у продюсера, дубли — идемпотентность на консюмере.
Rebalance останавливает все партиции внутри группы
Определив consumerGroup нагрузка делится между консюмерами кто вступил.




Из практики:
Если ключа нет по котрому  определяется партиция то у нас данные будут писаться в одну партицию до тех пор пока мы не достигнем 16кб батча при отправке.
