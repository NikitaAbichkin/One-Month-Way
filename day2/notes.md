cohesion(сплоченность) - связанность компонентов внутри сервиса( высокая - четко)

##### 4 ступени связанности ( от самого плохого к хорошему)

**Общая база данных** - первый сервис ее нагружает и второй ждет чтобы сделать свой инсерт, или мы решили поменять имя колонки то нужно менять сразу у нескольких сервисов.

**Общая библиотека DTO** - если мы используем общую библиотеку DTO, то нужно при добавлении нового поля  в конструктор нам нужно добавить это поле во всех сервисах, или мы поменяли имя у поля(DTO), то чтобы JackSon смог замапить  опять же нужно поменять название поля  у всех

**Синхронный вызов** - если мы внутри сервиса дергаем второй сервис, получается что у нас первый сервис зависит от  второго ( если второй будет обрабатывать 10 секунд то первый ждет 10 секунд)

**Хорошая ступень** - использование кафки или кролика, просто вкидываем в брокера сообщений наше сообщение и сразу даем пользователю промежуточный результат


##### Как разделить ?

Тест 1(  главный)
Одно уникальное бизнес решение( решение чего то одного  ) = отдельный сервис Каждый сервис отвечает только за свою часть и свои данные 

Свои данные 
Данные которые сервис достает  из бд и  может менять их и ему не нужно обращаться к другим сервисам чтобы принять решение.

##### Внутри каждого сервиса термин сущности может означать разное 

Нужно разделять по поведению

Есть товар на складе ( там нам нужен штрих код, позиция полки и количество на складе)
Есть товар на маркетплейсе (там нам нужна картинка, описание, стоимость)

Каждый хранит только свою сущность которая имеет смысл внутри контекста сервиса.

##### Почему добавление поля  другой структуры - плохо 

Если внутри нашей таблицы хранятся данные другого сервиса то при изменении формата сервиса который нам передает данные мы обязаны поменять  и формат у себя 
а это уже (высокая coupling  сервисов) изменения в одном затрагивают другой

Когда каждый сервис отвечает только за свою часть мы обезашиваем себя, мы отдаем и производим только свои данные а изменение формата ненаших данных нас не касается.

#### Паттерн Aggregate (объединение)

**Aggregate** — связка одной или нескольких сущностей внутри одного сервиса,
которые обязаны меняться вместе в одной транзакции, чтобы данные не стали
противоречивыми.

##### Правила

Нельзя иметь репозиторий для внутренних объектов, все изменения проходят
через корень (чтобы не нарушить согласованность с корнем).

Все изменения внутренних объектов проходят через методы корня
(чтобы сделать изменения И в корне И во внутреннем объекте).

Защита бизнес-правил — перед тем как изменить данные, мы в методе корня
проверяем бизнес-логику.

##### Связи

* **Внутри агрегата:** объектные связи JPA (`@OneToMany`, `@ManyToOne`),
  сущности неделимы.
* **На чужой агрегат — только плоский ID** (`Long userId`, `UUID orderId`),
  никаких `@ManyToOne`. Это работает в обе стороны:
  * чужой сервис — объекта нет физически, соединения с той базой нет;
  * **та же база** — объект технически доступен, и Hibernate сохранит его
    тем же коммитом. Барьер ставим сами, через ID.

##### Один агрегат = одна транзакция

Меняем несколько строк в разных таблицах, нужно сохранить их одним COMMIT,
иначе возникает противоречие (корень обновился, дочерняя строка нет).

##### Почему большой агрегат — плохо

**1. Блокировка корня — главное.**
Проверка правила требует, чтобы агрегат не менялся параллельно.
Корень блокируется целиком:

BEGIN
SELECT * FROM warehouse WHERE id=1 FOR UPDATE   ← строка занята
... работа ...
COMMIT                                           ← отпустило

Один корень на весь склад = все операции по всем товарам идут по очереди.
Резерв наушников блокирует резерв чайника, хотя они не связаны.

**2. Общий откат.**
Упало на одном товаре — откатились изменения по всем остальным
в этой же транзакции.

**3. Долгая транзакция.**
Дольше блокировка → длиннее очередь → больше падений по таймауту и повторов.

**4. Память.**
Чтобы изменить один товар, поднимаем в память весь агрегат.

## Правило размера
Агрегат делают настолько маленьким, насколько позволяет бизнес-правило.
Правило «сумма резервов ≤ остаток» касается одного товара
→ агрегат = один StockItem, а не весь Warehouse.
Резервы по разным товарам идут параллельно.

### Итог дня

**Цена сети.** Локальный вызов — наносекунды, сетевой — миллисекунды, разница в сотни тысяч раз. Три следствия: таймаут = неизвестный результат, общей транзакции нет, отказ частичный.

**Coupling.** Четыре уровня от худшего: общая база → общие модели → синхронный вызов → событие.

**Cohesion.** Резать по бизнес-функциям, не по слоям. Проверка: одно изменение → один сервис.

**Владение данными.** У каждого куска данных ровно один владелец-писатель. Остальные читают через API или копируют.

**Копия vs запрос.** Зафиксированное на момент события — копируем (адрес заказа). Актуальное — запрашиваем (email для письма).

**Aggregate.** Группа обьектов которые меняются внутри одной транзакции ради удовлетоворения бизнес логики. Снаружи только корень, дочерних репозиториев нет. На чужие агрегаты — ссылка по id.

**Размер агрегата.** Главной проблемой большого корня является то что у нас блокируется корень( гарантия того что подкорневые выражения никто не изменит).И мы счиатем на основе актуальных данных, но она накрывает весь агрегат целиком, те обьекты которые даже не участвуют в транзакции.

Мы не можем менять подкорневые выражения по причине того У нас условие менять через корень а на корне стоит блокировка.
