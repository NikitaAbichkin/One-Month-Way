Минусы распределенного монолита 

Распределенный монолит - система из нескольких сервисов , которые нельзя выкатывать и запускать по отдельности 


Общая код - если что то поменяли в нем то нужно менять во всех сервисах которые его используют ( было 5 параметров стало 6, везде возникает ошибка что не хватает параметра для создания объекта)

Общая бд 
1) Поменяли название колонки  - нужно менять во всех сервисах 
2) Непонятно кто отвечает за данные - проходят ли все ступени валидации
3) Общие ресурсы - тяжёлые запросы одного сервиса замедляют другой
4) База упала = уронили все сервисы 
5) Нельяз выбрать другую базу данных (Oracle, MySql, Postgress) - только одна 

##### Chatty-вызовы
Если сервису для обычной работы все время требуются данные другого сервиса это часто является причиной неправильного распределения 

Крупный APi - один метод отдает объект целиком
плохо: - Каждое поле это отдельный вызов для создания объекта

Batch 
Решение  проблемы путем одного запроса вместо нескольких - вместо того чтобы каждого пользователя доставать отдельно, достаем их всех пачкой 

Копия данных у себя
Не ходим в другой сервис а храним данные у себя в базе данных.
Как сделать: -  на втором сервисе ставим логику что если обновляем данные в бд то отправляем событие в кафку, а на нашем сервисе ставим слушать событие и по его приходу вносим изменения в свою бд 

##### Паттерн: Strangler fig
Ставим перед сервером Nginx который фильтрует запросы и потихоньку переводим монолит по одному сервису ( дописывая строчки ) в Nginx.Таблицы в это время все еще еще находится внутри одной бд ( антипаттрн )
Первыми выносят самые безопасные сервисы. Чтобы было некритично в случае падения

##### Компенсирующая операция
Если оплата прошла а Резервирование нет то ставим делаем противовес обратно и меняем баланс пользователя ( прибалвяем обратно 5000)

##### Outbox паттерн
 Сначала заносим данные в таблицу + OutboxTable(внутри одной транзакции). отдельный процесс читает `outbox` и отправляет в Kafka

#### Проблемы распредленного монолита ОЧЕНЬ КРАТКО

**Смена поля** - Смена одного поля влечет за собой деплой всех  зависящих сервисов
*Решение* - не нарушать контракт 
**Общий Jar c DTO**-  если у нас есть общий джар файл то это влечет за собой что у нас появлось новое поле или наоборот убавилось - один сервис ожидает получить параметр который другой сервис не шлет
*Решение*  - каждый сервис имеет свой код то как получить данные - те которые нужны конкретно ему 

**Общая бд** - один сервис нагружает сильнее, блокировки строк ( один сервис занимает строку ) и по логам у нас не видно этого , бд упала = упали все сервисы, сменна колонки влечет за собой перебилд всех сервисов.
*Решение* - у каждого сервиса сервиса должна быть своя бд, чтобы другой сервси в нее не ходил.

**Задержка таймАута** -  если у нас упал сервис а второй в это время на него ссылается то он ждет 5 секунд перед тем как выйти ( все это время поток занят), мы просто таким образом занимаем все потоки и другие сервисы не могут функционировать 
*Решение*: Сделать брокера сообщений, либо Outbox паттерн, или при таймауте сразу выкидывать ошибку
