Проблема:
Если клиент знает все  адреса сервисов и ходит сам то любое изменение(порта, ip адреса) ведет к тому что пользователю нужно обновлять приложение с новыми путями
(дублирование фильтра во всех сервисах )

**Api Gateway** - Ставим приложение которое будет заниматься тем куда перенаправлять запрос (клиент знает  только айпи адрес GateAway)

**CORS** - пометка для бразуера, чтобы он мог передать ответ джава скрипту. Сервер выполняет запрос  и отдает браузеру. Браузер смотрит на заголовок, и если его нет  то   он не отдает ответ джава скрипту.

**RouteFilter** - только  для одного маршрута (`orders/` -> добавить заголовок `Authorization`)
**GlobalFilter** - работает для всех маршутов перед отправкой (проверка JWT токена)

**BFF** - сервис который  делает несколько запросов (внутри сети), склеивает результат и возвращает. Быстрее потому что  всего 1 внешний запрос и N внутренних.(не нужно каждый раз дергать сервис через внешний запрос )


#### Rate limit  - ограничение частоты запросов 

**fixed window** - сколько запросов может  пройти  за  одну единицу времени 

**token bucket** - на сервере хранится   "ведро"(сколько запросов может отправить) которое пополняется раз в `n` секунд на `y` единиц

У каждого пользователя ведро N жетонов, запрос забирает 1 жетон. Жетоны досчитываются в момент запроса (с момента прошло запроса).Если записи нет  ведро у пользователя полное. Если жетонов нет  то 429.

Есть логика того как ведро пополнятся(5 токенов в секунду), 1 запрос = 1 токен, ТТЛ = 2с.
C такими характеристиками если пользователь не  делал запрос 2с и больше  то записи нет = у него  полное ведро  и  делается запись то что у него 9  записей. В случае если  у него осталось 4, прошла секунда и он делает запрос то мы видим что  прошла  секунда с прошлого 4 + 5  = 9, и вычитаем 1 получаем 8 запросов у пользователя.

**load balance** - балансировщик нагрузки, ставится перед gatAway ( отправляет в них запросы по очереди)

Если getAway несколько то нужно иметь общее ведро ( обычно используют Redis )

**TTL** - время жизни записи в редисе
**LUA скрипт** -  скрипт который редис выполняет атомарно в одно действие( другой поток не может записать данные промежуточно)

Поток - то что выполняет код
**Блокирующий вызов** - ждем  внешнего ответа (в этот момент ничего не делает но считается занятым)
**Неблокирующий вызов** - записываем байты в сокет, говорим ОС что когда байты придут, разбуди eventLoop(поток) и снова встаем в пул свободных потоков, (eventloop) поток принимает данные и обрабатывает.
*Разница:* В неблокирующем потоке первый пишущий поток не ждет ответа от  сервиса, он записал байты в буфер и ушел.

**Сокет** - объект внутри ядра операционной системы
##### что лежит в сокете ?
1) буфер приема - сюда записываются байты которые пришли 
2) буфер отправки - сюда записываются данные перед отправкой
3) Состояние TCP - (открыто/закрыто)
fileDescriptor - номер сокета

**epoll**  - операция, когда говорим  операционной системе следить  за  сокетом на  сетевом уровне(пришли байты )
**Event  loop**- поток  которого вызывает ОС когда байты пришли в сокет.
- Короткая операция - eventLoop обрабатывает ее сам 
- Длинная операция - вкидываем ее в пул  свободных потоков на выполнение 

Цепочка ровно такая
1. **Запись:** быстро скинули байты в буфер ядра и пошли дальше.
2. **Регистрация:** сказали ОС, за какими сокетами следить.
3. **Ожидание:** поток уснул на системном вызове, ожидая сигнала.
4. **Реакция:** пришли данные $\rightarrow$ ядро разбудило поток $\rightarrow$ поток прочитал байты и скинул  в  пул  свободных потоков на обработку, а сам пошел дальше  ждать пока его ОС вызовет(его задача передать данные из сокета в обработку)

### Основная суть:

ApiGateway  нужен для того чтобы перенаправлять запросы, фильтровать их, и обрабатывать большие объёмы за счет мультиплексирования( нет ожидания от внешнего сервиса)

Между  ApiGateway-s есть `редис-ведро`, где после прохождения фильтров спускаемся в редис чтобы понять  а может  ли пользователь сделать запрос (лимит на количество запросов в  секунду)

EventLoop поток который  в ожидании все время, пока байты не пришли он спит.(по табличке (сокет-функция)  выполняет действие)

Спим - Ос разбудила  - получили данные + обработали  - новый вызов(засыпаем)

Получили  запрос - записали в буфер отправки сокета - освободились - обрабатываем новый запрос 

Ведро
Есть логика того как ведро пополнятся, главное ограничить количество запросов в секунду у пользователя.
