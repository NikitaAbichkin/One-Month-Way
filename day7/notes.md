gRPC - кладет статус коды (OK,INVALID_ARGUMENT,NOT_FOUND,ALREADY_EXISTS) в трейлеры 
Трейлеры - заголовки которые идут после тела ответа 

**Interceptor** (перехватчик — код, который выполняется до и после вызова метода, но снаружи самого метода).


Основные правила изменения

1) добавлять поле можно - добавили следующим по счет, никаких проблем нет
2) Нельзя переиспользовать номер удаленного поля, мы помечаем его `reserved`, чтобы другое поле тоже случайно не имело  такой же порядок( защита на этапе компиляции кода)
3) Нельзя менять тип поля - тут просто приведение типов не сработает (ошибка)
4) Переименовывать поле можно свободно

| Критерий               | REST + JSON                                                                   | gRPC                                      |
| ---------------------- | ----------------------------------------------------------------------------- | ----------------------------------------- |
| Транспорт              | HTTP/1.1(обычно)                                                              | HTTP/2 мы используем                      |
| Контракт               | OpenApi                                                                       | proto                                     |
| Клиентский код         | руками или генерируется из OpenAPI                                            | генерируется из .proto (stub)`            |
| Ошибки                 | HTTP статусы(не всегда можон понять по ошибке можно ли делать ретрай или нет) | 17 gRPC-кодов(стандартных + текст ошибки) |
| Стриминг               | нет (нужны WebSocket/SSE)                                                     | 4 типа из коробки                         |
| дедлайн                | нету                                                                          | есть, через метаданные запроса            |
| читаемость             | легко читаемо                                                                 | нет, нужен инструмент (`grpcurl`)         |
| может ли юзать браузер | Напрямую(стандарт)                                                            | нет                                       |

Главный минус, в JavaScript нету доступа к упарвелнию низкоуровневыми (HTTP/2 фреймами), нужно ставит отдельный прокси.

Отсюда — где что применяют
**Публичный API наружу** (мобильные приложения, браузер, сторонние интеграции) → REST. (для удобности)

**Внутренние вызовы между микросервисами** (`order` → `inventory`, `order` → `payment`) → gRPC. Обе стороны соблюдают контракт и код не скомпилируется, если не соответствует proto-файлу

### Итог:
Главное различие между http кодами и gRPC в том что у gRPC( коды четко дают знать стоит ли повторять запрос или нет)

interceptor - перехватчик до и после вызова

REST vs gRPC - Rest используем с фронтом, чтобы он не ставил доп прокси и имелась возможность быстро  и легко проверить работоспособность бекенда. gRPC внутри микросверсивов, дает четкий контракт + скорость, стримы, трейлеры, дедлайны

JavaScript  решении о версии использовании протокола принимает бразуер а не JavaScript.И по дефлдту он не дает JavaScript доступа к трейлерам и управлению стримами.
